 # Feature Specification: メガミンクスの最後の層の画像ライブラリ（megaminx-image）

**Feature Branch**: `001-last-layer-image`

**Created**: 2026-11-24

**Status**: Draft

**Input**: User description: "メガミンクスの最後の層（上面）の画像を、回転記号の手順や色の指定から作る npm ライブラリ
megaminx-image。ルービックキューブの VisualCube のメガミンクス版のようなもの。既存の Web サイト
「Megaminx Image Editor」の状態計算と描画のロジックを画面から切り離し、Node.js とブラウザの両方で使える
ライブラリにする。"

## Clarifications

### Session 2026-11-24

- Q: PLL・OLL のケースのデータ（ケース名から手順を引く）をライブラリに入れるか → A: 入れる。本体とは別の入口
  （例：`megaminx-image/cases`）に分ける。元のデータを使ってよいかの確認はしない（依頼者の判断）
- Q: ライブラリのライセンス → A: MIT
- Q: 色の名前（"orange" など）も受け付けるか → A: 受け付けない。1 文字の色コードと `#rrggbb` だけ
- Q: 26 枚のステッカーの並び順 → A: サイトと同じ並び（U 面 11 枚 → 側面 15 枚、画像の上の頂点から反時計回り）
- Q: PLL・OLL のケースを別の向きで出したいときはどうするか → A: 設定 `rotate`（できた状態に U を k 回回した向き）
  を足す。alg・case・state のどれにも効く（計画のあとに依頼者が追加）

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 手順の文字列からケースの画像（SVG）を作る (Priority: P1)

メガミンクスの PLL・OLL の手順表や解説記事を作る開発者が、手順の文字列（例：`R U R' U'`）を渡すだけで、
最後の層の画像を SVG の文字列として受け取る。「その手順で揃うケース（case）」と「揃った状態から手順を
回した状態（alg）」のどちらでも作れる。色を手で塗る必要はない。

**Why this priority**: ライブラリの存在理由そのもの。これだけで手順表の画像を自動で作れ、
既存のサイトと同じ結果かどうか（いちばん大事な受け入れ条件）もここで確かめられる。

**Independent Test**: PLL・OLL の全ケースの手順を case と alg の両方で渡し、得られた 26 枚の色が
サイトから書き出した期待値と完全に一致すること、SVG の文字列が得られることを確かめる。

**Acceptance Scenarios**:

1. **Given** 揃った状態, **When** 手順 `R U R' U'` を alg として渡す, **Then** その手順を回した状態の
   最後の層の画像（SVG）が返り、26 枚の色はサイトで同じ手順を回したときと一致する
2. **Given** PLL の手順, **When** case として渡す, **Then** その手順で揃うケースの画像が返り、手順の中の
   持ち替え（y）の合計は打ち消されて、向きが元に戻った状態で描かれる
3. **Given** 何も指定しない設定, **When** 画像を作る, **Then** サイトと同じ既定の配色・形
   （U 面を真ん中、F 面を手前）・既定の大きさで描かれる
4. **Given** 同じ入力, **When** 何度・どの環境で作っても, **Then** SVG の文字列はバイト単位で同じになる

---

### User Story 2 - 読めない手順や間違った指定を、どこが悪いか分かるエラーで知る (Priority: P1)

開発者が手順や色を間違えて渡したとき、それらしい画像が黙って返るのではなく、どこが悪いかが分かる
エラーを受け取る。また、記号を正しい表記に書き直す・逆の手順を作る・無駄な手順をまとめる道具を使って、
手順の文字列を整えられる。

**Why this priority**: 間違った画像が手順表に紛れ込むと気づけない。読める・読めないの境目もサイトと
同じであることが受け入れ条件に含まれるため、Story 1 と同じく欠かせない。

**Independent Test**: 閉じていない括弧・対応しない「)」・知らない記号・回数だけの記号（`R 2`）などを
渡してエラーになること、そのメッセージで位置や記号が分かること、読める手順の範囲がサイトと同じことを
確かめる。

**Acceptance Scenarios**:

1. **Given** 手順 `(R U`, **When** 画像を作る, **Then** 括弧が閉じていないことと、その位置が分かるエラーになる
2. **Given** 手順 `R 2`, **When** 画像を作る, **Then** 回数だけの記号であることが分かるエラーになる
3. **Given** 手順 `r u bR' Y`, **When** 正しい表記に書き直す, **Then** `R U BR' y` が返る
4. **Given** 手順 `R R' U U`, **When** 無駄な手順をまとめる, **Then** `U2` が返る（括弧はまたがない）
5. **Given** 配色に無い面の色の指定, **When** 画像を作る, **Then** どの面が無いかが分かるエラーになる

---

### User Story 3 - 色・配色・見た目を指定する (Priority: P2)

開発者が、面ごとの配色、OLL 用の配色（U 面だけ色を残し、ほかを暗い灰色）、画像の大きさ、線の色、
背景（透明または色）を指定する。手順で作った状態の一部のステッカーの色だけを上書きしたり、
26 枚の色を 1 枚ずつ直接指定したりもできる。

**Why this priority**: OLL の手順表や独自の配色の記事には要るが、既定の配色だけでも P1 の価値は出る。

**Independent Test**: OLL 用の配色で OLL のケースを作り、U 面の色以外が暗い灰色になること、
大きさ・線の色・背景・上書きが SVG に反映されることを確かめる。

**Acceptance Scenarios**:

1. **Given** OLL 用の配色, **When** OLL のケースを作る, **Then** U 面の色のステッカーだけが薄い灰色で、
   ほかはすべて暗い灰色になる
2. **Given** 大きさ 400, **When** 画像を作る, **Then** 1 辺 400 の正方形の画像になり、細い線 4・太い線 8 の
   太さで描かれる
3. **Given** 26 枚の色の直接指定, **When** 画像を作る, **Then** 指定どおりの色で描かれる
4. **Given** 手順で作った状態と一部のステッカーの上書き, **When** 画像を作る, **Then** 上書きしたステッカーだけ
   色が変わる
5. **Given** 開始の状態（ほかの手順で崩した状態）, **When** alg・case を作る, **Then** その状態から計算される
6. **Given** PLL のケースの手順と向き 1, **When** case で画像を作る, **Then** 向き 0 の画像に U を 1 回
   （時計回りに 72°）回した画像になる

---

### User Story 4 - PNG を書き出す・canvas に描く・色の並びだけを取り出す (Priority: P3)

静的サイトのビルドで PNG ファイルを書き出したい開発者、Web アプリでその場で canvas に描きたい開発者、
独自の描き方をしたい開発者が、それぞれの形で結果を受け取る。

**Why this priority**: SVG があれば多くの用途は満たせる。PNG・canvas・色の並びは使い方を広げるもの。

**Independent Test**: 同じ入力で PNG（ファイル・バイト列）、canvas への描画、26 枚の色の並びを得て、
色の並びが文書の並び順どおりであること、PNG が SVG と同じ見た目であることを確かめる。

**Acceptance Scenarios**:

1. **Given** PNG 書き出し用の追加の部品を入れた Node.js, **When** PNG を書き出す, **Then** ファイルまたは
   バイト列が得られる
2. **Given** PNG 書き出し用の部品を入れていない環境, **When** PNG を書き出そうとする, **Then** 何を入れれば
   よいかが分かるエラーになり、SVG など他の機能はふつうに動く
3. **Given** ブラウザ, **When** canvas に描く, **Then** SVG と同じ見た目で描かれる
4. **Given** 手順, **When** 色の並びだけを取り出す, **Then** 文書に書いた並び順の 26 色が返る

---

### Edge Cases

- 空の手順（または空白だけ）は、揃った状態（alg・case とも）として扱う
- `R5`・`R0` のように 5 で割って 0 になる回数は、何もしない手順として扱う（サイトと同じ）
- `X2'` と `X'2` はどちらも反時計回りに 144°
- 入れ子の括弧と、括弧の後ろの回数・`'`（`((R U)2 R')'2` など）
- 全角のアポストロフィ（`’` など）・全角の括弧・全角の空白・読点・カンマが混ざった手順
- 空の括弧 `()` の扱いは、サイトの読み方に合わせる
- 26 枚より多い・少ない直接指定、範囲外のステッカーの上書きはエラー
- 知らない色コード・形の崩れた `#rrggbb` はエラー
- 0 以下・数でない画像の大きさはエラー
- DFR・DFL は DR・DL として読む。大文字・小文字は区別しない

## Requirements *(mandatory)*

### Functional Requirements

**画像の形**

- **FR-001**: 画像は、上から見た最後の層の 26 枚のステッカー（U 面の 11 枚：中心 1・辺 5・角 5 と、
  まわりの 5 つの側面の上段 15 枚：各面の左の角・辺・右の角）を描かなければならない
- **FR-002**: 正五角形の U 面を真ん中に、F 面を手前（下）に置き、ステッカーの境の細い線と、U 面の外周・
  側面の外周・側面の区切りの太い線を、今のサイトの画像と同じ形で描かなければならない
- **FR-003**: 画像の大きさ（正方形の 1 辺）、線の色、背景（透明または色）を指定できなければならない
- **FR-004**: 線の太さは画像の大きさに比例しなければならない（大きさ 200 のとき細い線 2・太い線 4）

**画像の作り方（入力）**

- **FR-005**: 揃った状態から手順を回した状態（alg）を作れなければならない
- **FR-006**: 手順で揃うケース（case）を作れなければならない。case は手順の逆を当てた状態とし、
  手順の中の持ち替え（y）の合計は打ち消して、向きが元に戻った状態にしなければならない
- **FR-007**: 26 枚のステッカーの色を 1 枚ずつ直接指定して（state）画像を作れなければならない
- **FR-008**: alg・case には開始の状態を渡せなければならない
- **FR-009**: alg・case で作った状態の一部のステッカーだけ、色を上書きできなければならない
- **FR-033**: 画像の向きを指定できなければならない。向き k は、できた状態に U を k 回（時計回りに 72° ずつ）
  回した向きとし、k は整数で 5 で割った余りとして読む（既定は 0。0 ならサイトと同じ）。alg・case・state の
  どれにも同じように効き、色の上書き（FR-009）は回したあとの位置に効く。整数でない向きはエラーにする

**回転記号**

- **FR-010**: 面 U F R L BR BL DR DL DBR DBL B D（12 面）と、全体の持ち替え y（U と同じ向き）を
  読まなければならない
- **FR-011**: X は面 X を外から見て時計回りに 72°、X' は反時計回り、X2 は時計回りに 144°、X2' と X'2 は
  反時計回りに 144° とし、3 以上の回数は 5 で割った余りとして読まなければならない
- **FR-012**: 括弧でまとめた手順、括弧の後ろの回数・`'`（逆の手順）、入れ子の括弧を読まなければならない
- **FR-013**: 大文字・小文字を区別せず、DFR・DFL を DR・DL の別名として読まなければならない
- **FR-014**: 全角のアポストロフィ・全角の括弧・全角の空白・読点・カンマを読まなければならない
- **FR-015**: 読めない手順（閉じていない括弧、対応しない「)」、知らない記号、回数だけの記号など）は、
  どこが悪いかが分かるエラーにしなければならない。黙って無視してはならない
- **FR-016**: 手順の道具として、記号を正しい表記に書き直す・逆の手順を作る・無駄な手順をまとめる
  （打ち消し合うものは消し、同じ面の続きは回数をまとめる。括弧はまたがない）機能を公開しなければならない
- **FR-017**: 手順の読み方（読める・読めない・エラーになる範囲と、読んだ結果）は既存のサイトと
  同じでなければならない

**色**

- **FR-018**: 面ごとの色（配色）を指定できなければならない。既定の配色はサイトと同じ
  （U 薄い灰色・F 水色・R オレンジ・BR 黄緑・BL ピンク・L レモン色・DR 紫・DBR 黄・B 青・DBL 赤・
  DL 緑・D 白）でなければならない
- **FR-019**: 色は、サイトと同じ 15 個の 1 文字の色コード（d 暗い灰色・u 薄い灰色・p ピンク・c レモン色・
  a 水色・o オレンジ・l 黄緑・b 青・y 黄・s 紫・g 緑・r 赤・w 白・x 黒・z ほぼ黒）または `#rrggbb` で
  指定できなければならない
- **FR-020**: 色の指定は FR-019 の 2 つの形（1 文字の色コード・`#rrggbb`）だけとし、色の名前（"orange" など）は
  知らない色としてエラーにしなければならない
- **FR-021**: OLL 用の配色（U 面の色だけを残し、ほかの面はすべて暗い灰色）を用意しなければならない
- **FR-022**: 配色に無い面の色・知らない色の指定は、どの指定が悪いか分かるエラーにしなければならない

**出力**

- **FR-023**: SVG の文字列を、追加の部品なしに Node.js でもブラウザでも作れなければならない
- **FR-024**: ブラウザでは canvas に描けなければならない
- **FR-025**: PNG（ファイル・バイト列）を書き出せなければならない。PNG に追加の部品が要る場合は任意とし、
  無いときは何が要るか分かるエラーにして、ほかの機能は動かなければならない
- **FR-026**: 画像を作らずに 26 枚のステッカーの色の並びだけを取り出せなければならない。並び順はサイトと
  同じとし、文書に書いて固定しなければならない。1 枚ずつの直接指定（FR-007）と上書き（FR-009）も同じ並び順を使う。
  画像の上の頂点を頂点 0 とし、反時計回りに頂点 0〜4、頂点 k と k+1 の間を辺 k とする（辺 2 が手前＝F 面）
  - 0：U 面の中心
  - 1 + 2k：U 面の角（頂点 k）
  - 2 + 2k：U 面の辺（辺 k）
  - 11 + 3k 〜 13 + 3k：辺 k の側面の上段（外から見て左の角・辺・右の角）
- **FR-027**: 同じ入力なら、出力はどの環境でも同じでなければならない（SVG はバイト単位で同じ）

**互換性・文書・範囲**

- **FR-028**: 既存のサイトにある PLL・OLL の全ケース（410 ケース：各ケースの手順と、そのケースになる手順）
  について、case と alg の両方で、サイトのロジックで作った 26 枚の色と完全に一致しなければならない
- **FR-029**: PLL・OLL の全ケース（410 ケース）のケース名・グループと手順（そのケースを揃える手順と、
  そのケースになる手順）を、本体とは別の入口から引けなければならない。本体だけを使う人は、ケースのデータを
  読み込まずに画像を作れなければならない
- **FR-030**: README に、記法・作り方 3 種・配色・出力・ステッカーの並び順を、ライブラリ自身で作り直せる
  画像の例と一緒に（英語で）書かなければならない
- **FR-031**: ライセンスは MIT とし、パッケージに LICENSE を含めなければならない
- **FR-032**: 次のものは作ってはならない：メガミンクス全体の展開図・立体の画像、練習・記録・進み具合・
  クラウド同期・表示言語の切り替えなどサイトのほかの機能、画像のクリックでステッカーを選ぶなどの画面の操作、
  WCA 形式のスクランブル（R++ D-- …）、URL で画像を返すサーバー。ただし、全体の展開図やサーバーをあとで
  足せないような作り方は避ける

### Key Entities *(include if feature involves data)*

- **手順（alg）**: 回転記号の並び。括弧・回数・逆の入れ子を含む。正しい表記・逆・まとめた形に変換できる
- **状態（state）**: 最後の層の 26 枚のステッカーそれぞれが、どの面の色か（または直接指定された色）。
  並び順はサイトと同じ（FR-026）
- **配色（scheme）**: 12 面それぞれの色。既定の配色と OLL 用の配色がある
- **色（color）**: 15 個の 1 文字の色コードのどれか、または `#rrggbb`
- **見た目の指定**: 画像の大きさ・線の色・背景
- **ケース（case data）**: PLL・OLL のケース名・グループと、揃える手順・そのケースになる手順。本体とは別の入口から引く（FR-029）

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: パッケージを入れた開発者が、5 行ほどのコードで手順から SVG を作れる
- **SC-002**: PLL・OLL の全 410 ケースについて、case と alg の両方で、26 枚の色がサイトの期待値と
  100% 一致する
- **SC-003**: 読める・読めない・エラーになる手順の判定が、用意した境目のテストケースすべてでサイトと一致する
- **SC-004**: ふつうのパソコンの Node.js で、1 枚の画像を 10ms 未満で作れる
- **SC-005**: 実行時に必ず入れなければならない追加のパッケージが 0 個（PNG の書き出しだけ任意の追加を許す）
- **SC-006**: 同じ入力を Node.js とブラウザで処理したとき、SVG の文字列が完全に一致する
- **SC-007**: README に、記法・作り方 3 種・配色・出力・ステッカーの並び順の説明と画像の例があり、
  例の画像はすべてライブラリ自身で作り直せる

## Assumptions

- ライブラリ名（npm のパッケージ名）は `megaminx-image` とする
- 正とする期待値は、既存のサイトのリポジトリ（手元の `MegaminxImageEditor`。状態計算は `js/megaminx-state.js`、
  描画は `js/megaminx-draw.js`、ケースの元データは `data/pll/algs_info.json`・`data/oll/algs_info.json`）の
  ロジックで書き出す。書き出し方は計画の段階で決める
- サイトのロジックとこの仕様の書き方が食い違うときは、サイトの振る舞いを正とする（原則 I）。違えるときは
  原則の変更として記録する
- 「ふつうのパソコン」は、ここ数年の一般的なノートパソコンを指す。時間は、読み込みの直後の 1 回目を除いた
  1 枚あたりの平均で測る
- 既定の画像の大きさは、サイトの画像と同じにする（具体的な値は計画で決める）
- 公開の README・API の名前・エラーのメッセージは英語、開発の文書は日本語（原則 VIII）
